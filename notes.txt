2026/09/08 - post-hoc-reporting fix, the one review-notes.md flagged
as real work and left alone on purpose ("Narrowing it to fire only
when the aggregate feeds a comparison or a signal is the right fix").

Checked the 4 real true-positive cases first (leak_full_series_std/
max/sum.py) before picking a rule, because they don't feed a Compare
at all - vol/high_water/total_volume get divided into a df column,
never compared. A "only flag if compared" rule would have silently
turned those into false negatives, the exact mistake review-notes.md
warned about ("deleting it throws away four real true positives").
So the rule implemented is narrower and different: suppress only when
the aggregate call sits directly inside a `return` statement (walking
up through wrapping arithmetic, via new ast parent-pointer annotation
- see annotate_parents/enclosing_statement in finder.py) - a value
handed straight back out of a function as its return value, with
nothing assigned into a dataframe column in this scope, matches
"report value" (Sharpe ratio, accuracy, ...) far more specifically
than "not compared" does, and none of the 4 leak_full_series cases are
inside a function at all, so the rule can't touch them.

  Awesome Oscillator backtest.py:285 (std) - NOT fixed, still flags.

known gap, left alone on purpose, same reasoning as before: the rule
only looks at the call's immediate enclosing statement. `m =
np.mean(x); return m / np.std(x)` (assign first, return the name on a
later line) is not caught, only a direct `return ...mean()...` is.
Tracing an assigned name forward to a later return would close this,
same shape of problem as the shift(lag) and window-variable tracking
already in collect_top_level_assignments, but scoped to a function
body with a return instead of the module top level - reasonable next
increment if this gap shows up in practice, not done today.

what changed: is_groupby_result() suppresses an aggregate whose
receiver is a .groupby(...) call - a categorical/cross-sectional
aggregate (by country and year here) isn't a time-ordered stat at all,
so the leak this tool looks for doesn't apply, independent of any
windowing question. is_inside_plot_call() walks up an aggregate call's
ancestors, within its own statement, and suppresses it if it's an
argument to a plotting method (plot, fill_between, scatter, bar, hist,
...) - a value feeding a chart isn't a trading decision, same
reasoning as the return-statement fix but reached through a plot call
instead of a return.

why the other two weren't touched:
  train/test-split bounding (Monte Carlo backtest.py:225,255) - the
  bounded name is df (from train_test_split(..., shuffle=False)), but
  the aggregate runs on returnn, built from df two arithmetic hops
  later (np.log(df['Close'].iloc[1:]/df['Close'].shift(1)...)).
  Catching this needs propagating "boundedness" through arbitrary
  expressions, and a value built from one bounded input mixed with
  something unbounded would get the same treatment - that's a real
  false-negative risk, not just an unfixed false positive.
  model.resid (Pair trading backtest.py:157) - same problem one layer
  worse: model comes from a call to an arbitrary local function
  (method(...)) fed a windowed argument. Treating "any function fed a
  bounded arg returns something bounded" as a rule is a broad
  assumption about function behavior this tool has no way to check,
  and review-notes.md already rejected a shallow pattern match fitted
  to this corpus for the same reason once (the original post-hoc-
  reporting decision). Left as a documented gap rather than guessed
  at.
